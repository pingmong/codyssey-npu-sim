# Mini NPU Simulator

코디세이 AI 올인원 입학연수 미션 3 레퍼런스 구현입니다.
입력 패턴과 필터를 위치별로 곱해 더하는 MAC(Multiply-Accumulate) 연산을 순수 Python 반복문으로 구현하고, 크기별 연산 시간을 측정합니다.

## 실행 방법

```bash
python main.py              # 1: 사용자 입력(3×3) / 2: data.json 분석
python -m tools.make_data   # 함정 케이스가 든 data.sample.json 생성 (멘토용)
```

## 파일 구조

미션 요구사항 번호에 맞춰 `src/` 아래 모듈을 나눴습니다. `src/__init__.py`가 있어야 `from src.mac import mac` 형태의 import가 동작합니다.

```
npu-sim/
├── main.py             # 09 실행 흐름 (모드 선택)
├── data.json           # 필터(size_5/13/25)와 패턴(size_N_idx) 데이터
├── README.md
├── src/
│   ├── __init__.py     # src를 패키지로 만드는 빈 파일
│   ├── matrix.py       # 01 데이터 구조 (n×n 리스트) + 패턴 생성기
│   ├── mode_input.py   # 02 모드 1: 3×3 필터/패턴 콘솔 입력 + 검증
│   ├── mode_json.py    # 03 모드 2: data.json 로드/스키마 검증 + 08 결과 리포트
│   ├── judge.py        # 04 라벨 정규화 + 06 epsilon 기반 판정
│   ├── mac.py          # 05 MAC 연산 (순수 반복문)
│   └── perf.py         # 07 성능 분석 (크기별 10회 평균 시간)
└── tools/
    └── make_data.py    # data.sample.json 생성기 (스키마 함정 케이스 포함)
```

## data.json 구조

코디세이에서 제공한 실제 `data.json`은 아래 구조입니다. (`meta` 키는 무시해도 됩니다.)

```json
{
  "meta": { "version": "1.0", "type": "json" },
  "filters": { "size_5": { "cross": [[...]], "x": [[...]] }, "size_13": {...}, "size_25": {...} },
  "patterns": { "size_5_1": { "input": [[...]], "expected": "x" }, "size_5_2": { ..., "expected": "+" }, ... }
}
```

- 패턴 키 `size_{N}_{idx}`에서 N을 추출해 `filters.size_{N}`을 선택합니다. 패턴은 크기당 2개(X, 십자가)씩 총 6개입니다.
- 라벨은 프로그램 내부에서 `Cross` / `X` 두 가지로 정규화합니다. (`'+'`, `'cross'` → Cross, `'x'` → X)
- 필터 값은 0/1이 아니라 **실수**입니다. 크기별로 가중치가 다르고(cross 1.0 / 0.3 / 1.0, x 0.1 / 0.3 / 0.1), 세 필터는 가운데 칸만 다른 값(0.9, 7.5, 4.9)을 가집니다. 이 값들이 아래 "동점" 케이스를 만드는 장치입니다.
- `tools/make_data.py`는 라벨 혼용·크기 불일치·잘못된 키 같은 스키마 함정이 들어간 `data.sample.json`을 따로 만듭니다. 실제 파일과 혼동하지 않도록 이름을 분리했습니다.

## 결과 리포트

### 실행 결과 요약

전체 6 / 통과 3 / 실패 3

| 케이스 | Cross 점수 | X 점수 | 판정 | expected | 결과 | 분류 |
|---|---|---|---|---|---|---|
| size_5_1 | 0.9 | 0.9 | UNDECIDED | X | FAIL | 수치 비교 |
| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS | - |
| size_13_1 | 0.3 | 14.7 | X | X | PASS | - |
| size_13_2 | 7.5 | 7.5 | UNDECIDED | Cross | FAIL | 수치 비교 |
| size_25_1 | 4.9 | 4.9 | UNDECIDED | X | FAIL | 수치 비교 |
| size_25_2 | 52.9 | 0.1 | Cross | Cross | PASS | - |

### 실패 원인 분석

실패 세 건은 모두 "수치 비교" 분류이며, 데이터 스키마나 MAC 로직의 문제가 아닙니다. 실제 data.json의 키 규칙, 배열 크기, 라벨은 모두 정상이어서 스키마 검증 단계에서 걸러진 케이스는 없었고, 라벨 정규화 덕분에 `'+'`와 `'x'`가 모두 표준 라벨로 통일되어 비교되었습니다.

세 건의 공통점은 Cross 점수와 X 점수가 수학적으로 정확히 같다는 것입니다. size_5_1은 X 패턴(1이 9칸)에 X 필터(0.1 × 9칸 = 0.9)를 겹친 점수와, 십자가 필터의 가운데 칸 0.9 하나만 겹친 점수가 같습니다. size_13_2는 십자가 패턴(25칸)에 십자가 필터 0.3 × 25 = 7.5와 X 필터 가운데 7.5가 같고, size_25_1은 X 필터 0.1 × 49 = 4.9와 십자가 필터 가운데 4.9가 같습니다. 필터의 가운데 칸 값(0.9, 7.5, 4.9)은 이 동점을 만들기 위해 의도적으로 설정된 값으로 보입니다.

이 동점이 부동소수점에서는 정확히 같지 않습니다. 실제 합산 결과는 0.9 vs 0.8999999999999999, 7.499999999999997 vs 7.5, 4.9 vs 4.899999999999999로, 0.1이나 0.3을 여러 번 누적하면서 생긴 1e-16~1e-15 수준의 오차가 남습니다. 만약 `score_a == score_b`로 비교했다면 이 오차 때문에 세 케이스가 각각 Cross, X, Cross로 "판정"되어 expected와 어긋나는 FAIL이 나고, 원인이 로직 오류처럼 보였을 것입니다. `abs(a - b) < 1e-9` 허용오차 정책을 적용했기 때문에 세 케이스는 UNDECIDED로 분류되었고, 결과적으로 FAIL이지만 그 사유가 "로직이 틀렸다"가 아니라 "두 필터가 구분하지 못하는 입력"임이 드러납니다.

따라서 이 실패는 프로그램이 고쳐야 할 결함이 아니라, 두 필터의 점수가 같은 입력에 대해 프로그램이 임의로 한쪽을 고르지 않았다는 증거입니다. 이런 입력을 정상적으로 판별하려면 필터 가중치 설계 자체를 바꾸어야 하며, 비교 정책을 느슨하게 하는 것으로는 해결되지 않습니다.

### 시간 복잡도 분석

| 크기 | 평균 시간(ms) | 연산 횟수(N²) | 3×3 대비 |
|---|---|---|---|
| 3×3 | 0.0007 | 9 | 1× |
| 5×5 | 0.0012 | 25 | 약 2× |
| 13×13 | 0.0051 | 169 | 약 7× |
| 25×25 | 0.0171 | 625 | 약 24× |

MAC 연산은 N×N의 모든 셀을 한 번씩 방문하므로 곱셈과 덧셈이 각각 N²번 일어납니다. 따라서 시간 복잡도는 O(N²)이고, 실제 측정에서도 N이 3에서 25로 약 8배 커질 때 시간은 약 24배 늘어 N²(약 69배)을 향해 증가하는 추세를 보였습니다. 작은 크기에서는 함수 호출이나 반복문 진입 같은 고정 비용이 상대적으로 커서 정확히 N²에 비례하지 않습니다. 시간 측정은 `time.perf_counter()`로 `mac()` 호출 구간만 10회 반복해 평균냈으며, 입력과 출력 시간은 포함하지 않았습니다. 절대 시간은 실행 환경마다 다르므로 비율의 추세로 해석해야 합니다.

### 보너스 1: 1차원 배열 최적화

2차원 리스트 `pattern[i][j]`는 바깥 리스트에서 i번째 행을 찾고, 다시 그 행에서 j번째 값을 찾는 두 단계 접근입니다. `flatten()`으로 길이 N²의 1차원 리스트로 바꾸면 `pattern_flat[k]` 한 번으로 끝나고 반복문도 하나로 줄어듭니다. 연산 횟수는 똑같이 N²이지만, 같은 입력·같은 반복 횟수로 측정했을 때 아래처럼 약 15~35% 빨라졌습니다. 변환(flatten) 시간은 측정에서 제외했습니다.

| 크기 | 2차원(ms) | 1차원(ms) | 개선율 |
|---|---|---|---|
| 3×3 | 0.0007 | 0.0005 | +33% |
| 5×5 | 0.0012 | 0.0008 | +35% |
| 13×13 | 0.0051 | 0.0035 | +32% |
| 25×25 | 0.0171 | 0.0145 | +15% |

실제 NPU나 GPU의 메모리도 2차원이 아니라 한 줄로 늘어선 1차원이고, 2차원 좌표 (i, j)는 i×N + j로 계산해서 접근합니다. 이 최적화는 그 구조를 흉내 낸 것입니다.

### 보너스 2: 패턴 생성기

`matrix.make_cross(n)`, `matrix.make_x(n)`으로 N×N 십자가와 X를 생성합니다. 모드 1에서 "자동 생성"을 고르면 N을 입력받아 필터 A(십자가), 필터 B(X)를 만들고 패턴을 십자가/X/직접 입력 중 선택해 같은 판정·성능 흐름을 그대로 탑니다. 모드 2의 3×3 성능 측정과 샘플 data.json 생성(`tools/make_data.py`)에도 같은 생성기를 사용합니다.

실제 AI 모델은 수백×수백 크기의 필터를 수천 개 사용하므로 이 N² 증가가 수억 번의 MAC 연산으로 이어집니다. 순차적으로 처리하는 CPU로는 감당하기 어렵고, 이 연산만 병렬로 처리하도록 설계된 NPU가 필요한 이유를 측정값으로 확인할 수 있었습니다.
