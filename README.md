# Mini NPU Simulator

코디세이 AI 올인원 입학연수 미션 3 레퍼런스 구현입니다.

- 입력 패턴과 필터를 같은 위치끼리 곱해 모두 더하는 **MAC(Multiply-Accumulate) 연산**을 순수 Python 반복문으로 구현합니다.
- 두 필터의 점수를 비교해 패턴을 판정하고, 크기별 연산 시간을 측정합니다.

## 실행 방법

```bash
python main.py              # 1: 사용자 입력(3×3) / 2: data.json 분석
python -m tools.make_data   # 함정 케이스가 든 data.sample.json 생성 (선택)
```

## 파일 구조

미션 요구사항 번호에 맞춰 `src/` 아래 모듈을 나눴습니다.

```
npu-sim/
├── main.py             # 09 실행 흐름 (모드 선택)
├── data.json           # 필터(size_5/13/25)와 패턴(size_N_idx) 데이터
├── README.md
├── src/
│   ├── __init__.py     # src를 패키지로 만드는 빈 파일
│   ├── matrix.py       # 01 데이터 구조 (n×n 리스트) + 패턴 생성기
│   ├── mode_input.py   # 02 모드 1: 3×3 필터/패턴 콘솔 입력 + 검증
│   ├── mode_json.py    # 03 모드 2: data.json 로드/스키마 검증 + 08 결과 리포트
│   ├── judge.py        # 04 라벨 정규화 + 06 epsilon 기반 판정
│   ├── mac.py          # 05 MAC 연산 (순수 반복문)
│   └── perf.py         # 07 성능 분석 (크기별 10회 평균 시간)
└── tools/
    └── make_data.py    # data.sample.json 생성기 (스키마 함정 케이스 포함)
```

> `src/__init__.py`가 있어야 `from src.mac import mac` 형태의 import가 동작합니다.

## data.json 구조

코디세이에서 제공한 실제 `data.json`의 구조입니다. `meta` 키는 사용하지 않습니다.

```json
{
  "meta": {
    "version": "1.0",
    "type": "json"
  },
  "filters": {
    "size_5": {
      "cross": [[...]],
      "x": [[...]]
    },
    "size_13": { ... },
    "size_25": { ... }
  },
  "patterns": {
    "size_5_1": {
      "input": [[...]],
      "expected": "x"
    },
    "size_5_2": {
      "input": [[...]],
      "expected": "+"
    },
    ...
  }
}
```

| 항목 | 규칙 | 프로그램에서의 처리 |
|---|---|---|
| 패턴 키 | `size_{N}_{idx}` | N을 꺼내 `filters.size_{N}`을 선택 |
| 패턴 개수 | 크기당 2개 (X, 십자가) | 총 6개 |
| expected | `'+'`, `'x'` 등 표기 혼용 | `Cross` / `X`로 정규화 후 비교 |
| 필터 값 | 0/1이 아닌 **실수** | 가운데 칸만 다른 값(0.9, 7.5, 4.9) |

- 크기별 필터 가중치: cross는 1.0 / 0.3 / 1.0, x는 0.1 / 0.3 / 0.1 입니다.
- 가운데 칸 값(0.9, 7.5, 4.9)이 아래 결과 리포트의 "동점" 케이스를 만듭니다.
- `tools/make_data.py`는 라벨 혼용·크기 불일치·잘못된 키 같은 함정을 넣은 `data.sample.json`을 따로 만듭니다. 실제 파일과 헷갈리지 않도록 이름을 분리했습니다.

## 결과 리포트

### 실행 결과 요약

**전체 6 / 통과 3 / 실패 3**

| 케이스 | Cross 점수 | X 점수 | 판정 | expected | 결과 | 분류 |
|---|---|---|---|---|---|---|
| size_5_1 | 0.9 | 0.9 | UNDECIDED | X | FAIL | 수치 비교 |
| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS | - |
| size_13_1 | 0.3 | 14.7 | X | X | PASS | - |
| size_13_2 | 7.5 | 7.5 | UNDECIDED | Cross | FAIL | 수치 비교 |

| size_25_2 | 52.9 | 0.1 | Cross | Cross | PASS | - |

### 실패 원인 분석

**1. 데이터나 로직 문제가 아님**

실패 3건은 모두 "수치 비교" 분류입니다.

- 키 규칙, 배열 크기, 라벨이 모두 정상이라 스키마 검증에서 걸러진 케이스는 없었습니다.
- 라벨 정규화로 `'+'`와 `'x'`가 표준 라벨로 통일되어 비교되었습니다.

**2. 두 점수가 수학적으로 같도록 설계된 입력**

| 케이스 | 한쪽 점수 | 다른 쪽 점수 |
|---|---|---|
| size_5_1 (X) | X 필터 0.1 × 9칸 = 0.9 | 십자가 필터 가운데 칸 = 0.9 |
| size_13_2 (십자가) | 십자가 필터 0.3 × 25칸 = 7.5 | X 필터 가운데 칸 = 7.5 |
| size_25_1 (X) | X 필터 0.1 × 49칸 = 4.9 | 십자가 필터 가운데 칸 = 4.9 |

필터의 가운데 칸 값은 이 동점을 만들기 위해 의도적으로 정한 값으로 보입니다.

**3. 부동소수점에서는 정확히 같지 않음**

0.1이나 0.3을 여러 번 더하면 1e-16 ~ 1e-15 수준의 오차가 남습니다.

| 케이스 | 실제 합산 결과 |
|---|---|
| size_5_1 | 0.9 vs 0.8999999999999999 |
| size_13_2 | 7.499999999999997 vs 7.5 |
| size_25_1 | 4.9 vs 4.899999999999999 |

- `score_a == score_b`로 비교했다면 이 오차 때문에 각각 Cross, X, Cross로 판정되어, 로직 오류처럼 보이는 FAIL이 났을 것입니다.
- `abs(a - b) < 1e-9` 허용오차 정책을 적용해 세 케이스는 UNDECIDED가 되었고, 실패 사유가 "두 필터가 구분하지 못하는 입력"으로 정확히 드러났습니다.

**4. 결론**

이 실패는 고쳐야 할 결함이 아니라, 점수가 같은 입력에서 프로그램이 임의로 한쪽을 고르지 않았다는 증거입니다. 이런 입력을 판별하려면 비교 정책을 느슨하게 할 것이 아니라 필터 가중치 설계를 바꿔야 합니다.

### 시간 복잡도 분석

| 크기 | 평균 시간(ms) | 연산 횟수(N²) | 3×3 대비 |
|---|---|---|---|
| 3×3 | 0.0007 | 9 | 1× |
| 5×5 | 0.0012 | 25 | 약 2× |
| 13×13 | 0.0051 | 169 | 약 7× |
| 25×25 | 0.0171 | 625 | 약 24× |

- MAC 연산은 N×N의 모든 칸을 한 번씩 방문하므로 곱셈과 덧셈이 각각 N²번 일어납니다. 시간 복잡도는 **O(N²)** 입니다.
- N이 3에서 25로 약 8배 커질 때 시간은 약 24배 늘었습니다. N² 비율(약 69배)보다 작은 이유는, 작은 크기일수록 함수 호출이나 반복문 진입 같은 고정 비용의 비중이 크기 때문입니다.
- 측정 방법: `time.perf_counter()`로 `mac()` 호출 구간만 10회 반복해 평균을 냈고, 입력·출력 시간은 포함하지 않았습니다.
- 절대 시간은 실행 환경마다 다르므로 비율의 추세로 해석해야 합니다.

### 보너스 1: 1차원 배열 최적화

- 2차원 리스트 `pattern[i][j]`는 행을 찾고 다시 열을 찾는 두 단계 접근입니다.
- `flatten()`으로 길이 N²의 1차원 리스트로 바꾸면 `pattern_flat[k]` 한 번으로 접근하고, 반복문도 하나로 줄어듭니다.
- 연산 횟수는 똑같이 N²이지만, 같은 입력·같은 반복 횟수로 측정했을 때 약 15~35% 빨라졌습니다. (flatten 시간은 측정에서 제외)

| 크기 | 2차원(ms) | 1차원(ms) | 개선율 |
|---|---|---|---|
| 3×3 | 0.0007 | 0.0005 | +33% |
| 5×5 | 0.0012 | 0.0008 | +35% |
| 13×13 | 0.0051 | 0.0035 | +32% |
| 25×25 | 0.0171 | 0.0145 | +15% |

실제 NPU나 GPU의 메모리도 한 줄로 늘어선 1차원이고, 2차원 좌표 (i, j)는 `i × N + j`로 계산해 접근합니다. 이 최적화는 그 구조를 흉내 낸 것입니다.

### 보너스 2: 패턴 생성기

- `matrix.make_cross(n)`, `matrix.make_x(n)`으로 N×N 십자가와 X를 만듭니다.
- 모드 1에서 "자동 생성"을 고르면 N을 입력받아 필터 A(십자가), 필터 B(X)를 만들고, 패턴은 십자가 / X / 직접 입력 중에서 고릅니다. 이후 판정·성능 흐름은 같습니다.
- 모드 2의 3×3 성능 측정과 `tools/make_data.py`의 샘플 생성에도 같은 생성기를 사용합니다.

### 정리

실제 AI 모델은 작은 필터를 이미지의 모든 위치와 수많은 레이어에 반복 적용하므로, N²로 늘어나는 연산이 수억 번의 MAC으로 이어집니다. 순차적으로 처리하는 CPU로는 감당하기 어렵고, 이 연산을 병렬로 처리하도록 설계된 NPU가 필요한 이유를 측정값으로 확인할 수 있었습니다.
